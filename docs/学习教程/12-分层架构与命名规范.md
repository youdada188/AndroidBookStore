# 12 · 分层架构与命名规范

> **本篇你会学到**：为什么代码要分四层、Repository 是干什么的、**每个类名和变量名背后的思考**。
> 这是全教程最重要的一篇，也是答辩最容易加分的部分。

---

## 12.1 先看问题：所有代码写在一个文件里行不行

假设你把"读数据库 + 显示列表 + 处理点击"全写在 `MainActivity` 里：

```java
public class MainActivity extends Activity {
    // 建表 SQL
    // 查询图书
    // 解析 JSON
    // 渲染列表
    // 处理点击
    // ... 2000 行
}
```

**会发生什么：**

| 问题 | 具体表现 |
|---|---|
| 找不到代码 | 想改"价格显示"，要在一堆 SQL 里翻 |
| 改一处崩一片 | 改查询逻辑，不小心影响了界面 |
| 无法复用 | 另一个页面也要查图书，只能复制粘贴 |
| 无法测试 | 数据库逻辑和界面绑死，没法单独测 |
| 多人协作冲突 | 两个人改同一个文件，天天冲突 |

**解决办法：分层。** 每层只干一件事，层与层之间通过**明确的接口**通信。

## 12.2 项目的四层结构

```
┌─────────────────────────────────────────┐
│  ui 层（界面）                            │
│  MainActivity / HomeFragment / Adapter   │
│  职责：显示数据、接收用户操作               │
│  不知道：数据从哪来、SQL 怎么写             │
└──────────────────┬──────────────────────┘
                   │ 调用方法，传/收 Java 对象
┌──────────────────▼──────────────────────┐
│  data 层（数据）                          │
│  BookRepository                          │
│  职责：提供"取书店""下单"这样的业务方法      │
│  不知道：界面长什么样                       │
└──────────────────┬──────────────────────┘
                   │ 执行 SQL
┌──────────────────▼──────────────────────┐
│  data 层（存储）                          │
│  BookDbHelper / JsonSeeder               │
│  职责：建表、升级、导入初始数据              │
│  不知道：谁在查、查来干什么                  │
└──────────────────┬──────────────────────┘
                   │
┌──────────────────▼──────────────────────┐
│  SQLite 数据库文件                        │
└─────────────────────────────────────────┘

        ┌────────────────────────┐
        │  model 层（贯穿所有层）   │
        │  Book / Store / Order   │
        │  职责：只描述数据结构      │
        │  不知道：任何业务逻辑      │
        └────────────────────────┘
```

### 每层的"红线"

| 层 | 可以做什么 | **绝对不可以做什么** |
|---|---|---|
| `ui` | 调 Repository、操作 View、弹 Toast | 写 SQL、直接开数据库 |
| `data` | 执行 SQL、返回 model 对象 | 弹 Toast、引用 `R.id.xxx`、`startActivity` |
| `model` | 存字段、提供 getter | 查数据库、格式化界面文字 |
| `util` | 纯函数工具 | 依赖具体业务 |

**怎么检查有没有越界？** 看 import：

```java
// data/BookRepository.java 的 import
import android.content.ContentValues;
import android.database.Cursor;
import android.database.sqlite.SQLiteDatabase;
import com.yzc.bookmall.model.Book;
// ↑ 没有 import 任何 ui 包，也没有 import android.widget
```

**如果 `BookRepository` 里出现了 `import android.widget.Toast`，就说明分层被破坏了。**

## 12.3 Repository 模式：为什么要多这一层

初学者常问：**"`BookDbHelper` 已经能操作数据库了，为什么还要 `BookRepository`？"**

因为它们的职责完全不同：

| | `BookDbHelper` | `BookRepository` |
|---|---|---|
| 关注点 | **数据库本身**：怎么建表、怎么升级 | **业务需求**：取书店、下单、加收藏 |
| 方法名 | `onCreate`、`onUpgrade` | `getStores`、`createOrder` |
| 类比 | 仓库管理员（管货架） | 采购员（你要什么他去拿） |

### 如果只有 Helper 会怎样

`HomeFragment` 想显示书店列表，就得自己写 SQL：

```java
// 界面层被迫写 SQL —— 灾难
String sql = "SELECT s.id, s.name, ... FROM stores s ORDER BY s.id ASC";
Cursor c = dbHelper.getReadableDatabase().rawQuery(sql, null);
while (c.moveToNext()) { ... }
```

问题：

1. **SQL 散落在各处**：改表结构要改 10 个界面
2. **界面层被迫懂数据库**：写界面的人得会 SQL
3. **无法复用**：书店详情页也要查书店，再复制一遍

### 有了 Repository 之后

```java
// 界面层只需要一句话
List<Store> stores = repository.getStores();
```

**所有 SQL 集中在 `BookRepository` 一个文件里（189 行）。** 改表结构只改这里，界面一行不用动。

> **`Repository` 直译"仓库/仓储"。** 它是领域驱动设计（DDD）里的概念，意思是"**数据的存取入口**"。你告诉它要什么，它负责从各种数据源（数据库、网络、缓存）取来给你，你不关心它怎么取的。

### 一个更实际的例子：换数据源

假设哪天老师要求"改成从网络接口取数据"。有 Repository 的话：

```java
// 只改 Repository 内部
public List<Store> getStores() {
    if (hasNetwork()) {
        return fetchFromApi();      // 从网络取
    } else {
        return queryFromDb();       // 从数据库取
    }
}
```

**界面层一行都不用改。** 因为它调的始终是 `getStores()`。

## 12.4 一次数据请求的完整旅程

以"首页显示书店列表"为例，跟一遍：

```
① HomeFragment.onResume()
        ↓ 调用
② repository.getStores()
        ↓ 内部
③ dbHelper.getReadableDatabase()        ← 拿到数据库连接
        ↓
④ db.rawQuery(sql, null)                ← 执行 SQL
        ↓ 返回
⑤ Cursor（指向结果集的游标）
        ↓ 循环
⑥ mapStore(cursor)                      ← 把一行转成 Store 对象
        ↓ 返回
⑦ List<Store>（Java 对象列表）
        ↓ 传回
⑧ adapter.submit(stores)                ← 交给适配器
        ↓
⑨ RecyclerView 显示出来
```

**每一层的输入输出类型：**

| 步骤 | 输入 | 输出 |
|---|---|---|
| ② | 无 | `List<Store>` |
| ④ | SQL 字符串 | `Cursor` |
| ⑥ | `Cursor` 的一行 | `Store` 对象 |
| ⑧ | `List<Store>` | 无（直接改 UI） |

**关键点：`Cursor` 不会离开 data 层。**

`Cursor` 是数据库的产物，如果把它传到界面层，界面就依赖了数据库。所以在 `getStores()` 内部就把它转成了 `List<Store>`，**出去的全是纯 Java 对象**。

## 12.5 命名六原则

### 原则 1：名字要说明"是什么"，不是"怎么做的"

| ❌ 差 | ✅ 好 | 原因 |
|---|---|---|
| `list1` | `stores` | 说出内容是什么 |
| `data` | `books` | `data` 太泛，什么都是 data |
| `temp` | `currentBook` | 说明是"当前这本书" |
| `flag` | `isLoggedIn` | 说明这个标志代表什么 |

### 原则 2：能读出来，别用缩写

| ❌ | ✅ |
|---|---|
| `usrNm` | `username` |
| `btnSub` | `submitButton` |
| `qty` | `quantity` |
| `desc` | `description` |

**例外**：`id`、`url`、`db`、`ui` 这种全世界都认的缩写可以用。

### 原则 3：布尔值用 `is` / `has` / `can` 开头

```java
private boolean isDefault;        // 是否默认地址
private boolean recommended;      // 项目里叫 recommended，用 isRecommended() 读
private boolean isLoggedIn();     // 方法
private boolean canReview(...);   // 能不能评价
private boolean hasReviewed(...); // 有没有评过
```

**读起来像一句话**：`if (session.isLoggedIn())` —— "如果会话已登录"。

### 原则 4：单位写进名字

```java
private final int priceFen;          // 分
private int goodsFen;                // 分
private long createdAt;              // 毫秒时间戳
private static final long FAKE_LOADING_DELAY = 300L;   // 毫秒
```

**为什么？** 因为 `price` 你不知道是元还是分，`timeout` 你不知道是秒还是毫秒。**单位写进名字，永远不会搞错。**

项目里所有金额变量都带 `Fen`，这是最值得学的命名习惯。

### 原则 5：集合用复数

```java
private final List<Book> items;              // 多个
private final Set<Long> selectedBookIds;     // 多个 ID
private List<Store> stores;                  // 多个
```

### 原则 6：常量全大写，单词间下划线

```java
private static final int TOTAL_SECONDS = 3;
private static final String DATABASE_NAME = "book_mall.db";
private static final int REQUEST_ADDRESS = 1001;
```

## 12.6 类名后缀词典（最重要的一张表）

Android/Java 世界里，**类名的后缀直接暴露了它的职责**。看到后缀就知道它是干嘛的：

| 后缀 | 含义 | 项目里的例子 | 职责 |
|---|---|---|---|
| `Activity` | 一个页面 | `MainActivity`、`LoginActivity` | 承载一屏 UI |
| `Fragment` | 页面片段 | `HomeFragment` | 寄生在 Activity 里的 UI 块 |
| `Adapter` | 适配器 | `BookAdapter`、`CartAdapter` | 把数据适配成列表项 |
| `Holder` | 持有者 | `BookHolder` | 缓存一行里的控件引用 |
| `Listener` | 监听器 | `CartAdapter.Listener` | 回调接口 |
| `View` | 自定义控件 | `StateView` | 可复用的 UI 组件 |
| `Repository` | 仓储 | `BookRepository` | 数据存取入口 |
| `Helper` | 帮手 | `BookDbHelper` | 辅助某个框架类工作 |
| `Manager` | 管理器 | `SessionManager` | 管理一类状态 |
| `Seeder` | 播种器 | `JsonSeeder` | 灌初始数据 |
| `Utils` | 工具 | `FormatUtils` | 纯静态工具方法 |
| `Model` / 无后缀 | 实体 | `Book`、`Store`、`Order` | 数据结构 |

### 为什么 `BookDbHelper` 叫 Helper 不叫 Manager

- **`Helper`** 通常表示"**辅助某个框架类**"。`SQLiteOpenHelper` 是 Android 提供的基类，我们继承它，所以叫 `BookDbHelper`（书的数据库帮手）。
- **`Manager`** 表示"**管理一类资源或状态**"。`SessionManager` 管理登录会话。

**判断标准**：继承框架基类的叫 Helper，自己独立管事的叫 Manager。

### 为什么 `FormatUtils` 用 Utils 而且全是 static

```java
public final class FormatUtils {
    private FormatUtils() { }        // ① 私有构造，禁止 new
    public static String formatPrice(int priceFen) { ... }   // ② 全是 static
}
```

**① 私有构造方法** —— 让外部无法 `new FormatUtils()`。因为工具类不需要对象，只需要方法。

**② 全 static** —— 直接 `FormatUtils.formatPrice(5900)` 调用，不用创建实例。

**这叫"工具类模式"**，JDK 里的 `Math`、`Collections` 都是这个套路。

> **`final` 修饰类** = 不允许被继承。工具类没有继承的意义，加上更严谨。

## 12.7 变量名逐个解释

这是本篇的核心。把项目里"看起来奇怪"的变量名全过一遍。

### 金额类

| 变量名 | 拆解 | 为什么这么叫 |
|---|---|---|
| `priceFen` | price + Fen | 价格，单位**分**。`Fen` 是拼音，比 `cents` 更符合中文项目习惯 |
| `goodsFen` | goods + Fen | **商品**总额（不含运费和优惠） |
| `deliveryFen` | delivery + Fen | **配送**费 |
| `discountFen` | discount + Fen | **优惠**金额 |
| `totalAmountFen` | total + amount + Fen | **总金额**（实付） |
| `priceSnapshotFen` | price + Snapshot + Fen | **价格快照**（下单时的价格，不随改价变化） |
| `thresholdFen` | threshold + Fen | **门槛**（满多少可用券） |
| `minOrderFen` | min + order + Fen | **起送价** |

**为什么用拼音 `Fen` 而不是 `Cents`？**

`cents` 是"美分"，用在人民币上不准确。中文项目里用 `Fen` 更直观。也可以写 `priceInCents`，但项目选了更短的 `priceFen`。

### 资源类

| 变量名 | 拆解 | 为什么 |
|---|---|---|
| `coverResId` | cover + **Res**ource + **Id** | 封面**资源 ID**（`R.drawable.xxx` 那个整数） |
| `R.layout.item_book` | Resource.layout.文件名 | `R` 就是 Resource 的缩写 |

**为什么叫 `ResId` 不叫 `ImageId`？** 因为它指向的是"资源"，可能是 drawable、mipmap、raw，不一定是图片。

### 数据访问类

| 变量名 | 拆解 | 为什么 |
|---|---|---|
| `dbHelper` | **Db** + Helper | 数据库帮手 |
| `repository` | repository | 仓储，数据入口 |
| `preferences` | preferences | 复数，因为存多条键值对 |
| `cursor` / `c` | cursor | 游标，指向结果集 |
| `values` / `v` | values | `ContentValues` 装的是"一堆值" |

### 界面类

| 变量名 | 拆解 | 为什么 |
|---|---|---|
| `stateView` | state + View | **状态**视图（加载/空/错误） |
| `countdownView` | countdown + View | **倒计时**文本控件 |
| `quantityView` | quantity + View | **数量**文本控件 |
| `favoriteView` | favorite + View | **收藏**按钮 |
| `selectAll` | select + all | **全选**复选框 |
| `checkoutButton` | checkout + Button | **结算**按钮 |

**规律：`控件类型` 做后缀，`业务含义` 做前缀。** `tv_` / `iv_` 是 XML 里的前缀，Java 变量里用完整单词 `View` / `Button`。

### 适配器类

| 变量名 | 为什么 |
|---|---|
| `items` | 通用叫法，表示"列表里的项"。不用 `books` 是因为 Adapter 应该通用 |
| `listener` | 监听器，回调接口的实例 |
| `holder` | 持有者，指 ViewHolder |
| `position` | 位置，第几项（从 0 开始） |
| `viewType` | 视图类型（多布局时用） |
| `parent` | 父容器 |
| `itemView` | 一行的根 View |

### 状态标志类

| 变量名 | 拆解 | 为什么 |
|---|---|---|
| `containerFilled` | container + filled | 容器**已填充**（过去分词表示"已经…了"） |
| `navigated` | navigated | **已跳转**（防止重复跳转） |
| `bindingSelectAll` | binding + selectAll | **正在绑定**全选框（防止监听器回环） |
| `isDefault` | is + default | 是否默认地址 |
| `pickMode` | pick + Mode | **选择模式**（同一个页面两种用途） |
| `updateFirst` | update + first | **先更新**（再插入） |
| `loggedIn` | logged + in | 已登录 |

### 重点讲三个"看起来奇怪"的

#### ① `bindingSelectAll`

```java
private boolean bindingSelectAll;

private void updateSummary() {
    ...
    bindingSelectAll = true;                    // ① 标记"我要改 UI 了"
    selectAll.setChecked(adapter.isAllSelected());   // ② 改 UI
    bindingSelectAll = false;                   // ③ 改完了
}

selectAll.setOnCheckedChangeListener((buttonView, checked) -> {
    if (bindingSelectAll) return;               // ④ 如果是"程序改的"，忽略
    adapter.setAllSelected(checked);
});
```

**问题背景**：`setChecked()` 会触发 `OnCheckedChangeListener`。如果监听器里又去改 adapter 的选中状态，adapter 又回头更新 UI，就会**无限循环**。

**解决**：加一个"我正在改"的标志。程序改的时候设 true，监听器看到 true 就直接 return。

> **命名解读**：`binding` 是"绑定/回填"的意思——把数据状态**回填**到 UI 上。这是 Android 开发里的常用说法（DataBinding 库也是这个思路）。

#### ② `remaining` 和 `TOTAL_SECONDS`

```java
private static final int TOTAL_SECONDS = 3;    // 总共 3 秒
private int remaining = TOTAL_SECONDS;         // 还剩几秒
```

**一对反义词做命名对照**：`TOTAL`（总）vs `remaining`（剩余）。

`remaining` 用 `-ing` 结尾，表示"**正在进行中的量**"。类似的还有 `loading`（加载中）、`pending`（待处理）。

#### ③ `loader` 和 `ticker`

```java
private final Runnable loader = this::loadNow;    // 加载任务
private final Runnable ticker = new Runnable() {  // 滴答任务
    @Override public void run() { remaining--; ... }
};
```

**`-er` 后缀表示"做某件事的东西"**：

| 名字 | 字面意思 | 实际作用 |
|---|---|---|
| `loader` | 加载者 | 执行加载的任务 |
| `ticker` | 滴答者 | 每秒执行一次的定时任务 |
| `handler` | 处理者 | 投递和处理消息 |
| `adapter` | 适配者 | 把数据适配成 View |

**为什么 `loader` 存成字段，`ticker` 用匿名类？**

两个都需要存成字段——因为 `removeCallbacks()` 要用**同一个对象**才能取消。区别只是 `loader` 用了方法引用（`this::loadNow`）更简洁，`ticker` 需要访问 `remaining` 等字段所以写成完整的匿名类。

## 12.8 方法名命名

| 前缀 | 含义 | 项目里的例子 |
|---|---|---|
| `get` | 取一个值 | `getStores()`、`getBookById()`、`getPriceFen()` |
| `set` | 设置值 | `setFavorite()`、`setDefaultAddress()` |
| `is` / `has` / `can` | 布尔判断 | `isLoggedIn()`、`hasReviewed()`、`canReview()` |
| `load` | 加载（异步） | `load()`、`loadBooks()`、`loadStore()` |
| `bind` | 绑定数据到 UI | `bindBook()`、`bindAddress()`、`bindAmounts()` |
| `show` | 显示某种状态 | `showLoading()`、`showEmpty()`、`showError()` |
| `submit` | 提交数据 | `adapter.submit(books)`、`submit()`（提交订单） |
| `update` | 更新 | `updateCartQuantity()`、`updateTotal()` |
| `create` / `add` / `delete` | 增删 | `createOrder()`、`addToCart()`、`deleteCartItem()` |
| `toggle` | 切换（开关） | `toggleFavorite()` |
| `format` | 格式化 | `formatPrice()`、`formatDate()` |
| `parse` | 解析 | `Integer.parseInt()` |
| `validate` | 校验 | `validateReceiver()` |
| `generate` | 生成 | `generateOrderNo()` |
| `clear` | 清空 | `clearSession()`、`clearCurrentUserData()` |

### `load` vs `loadNow` 的区别

```java
private void load() {                       // 带延迟的"开始加载"
    stateView.showLoading();
    handler.removeCallbacks(loader);
    handler.postDelayed(loader, 300);
}

private void loadNow() {                    // 立刻执行真正的加载
    if (!isAdded()) return;
    List<Store> stores = repository.getStores();
    ...
}
```

- `load()` = "发起一次加载"（含延迟、状态切换）
- `loadNow()` = "**现在就**加载"（纯数据操作）

**`Now` 后缀表示"立即执行"**，和带延迟的 `load` 区分开。

### `bind` 系列的规律

```java
private void bindBook(Book book) { ... }        // 把 Book 的数据填到界面上
private void bindAddress() { ... }              // 把地址填到界面上
private void bindAmounts() { ... }              // 把金额填到界面上
private void bindReviews() { ... }              // 把评价填到界面上
```

**`bind` = "绑定"，即"把数据塞进 UI 控件"**。这类方法通常是一长串 `findViewById(...).setText(...)`。

## 12.10 反例对照表（自查用）

| ❌ 不好的命名 | ✅ 项目里的做法 | 问题在哪 |
|---|---|---|

| 概念 | 要点 |
